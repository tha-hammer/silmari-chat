### Memory Integration (Zettel)

The Algorithm has a persistent memory layer reachable via the `zettel` CLI (`~/.local/bin/zettel`) which talks to the cosmic-agent-memory engine over an SSH tunnel at `http://localhost:8787`. Use it to **recall before you reason** and **save what you learned** so each Algorithm run compounds with prior runs instead of starting from zero.

**Two mandatory integration points:**

1. **OBSERVE entry — RECALL.** Immediately after creating the PRD stub and before reverse engineering, run:
   ```bash
   zettel recall "{8-word task description}" -l 5 -d connected
   ```
   If results come back, summarize the top 1-3 hits in the OBSERVE output under a `🧠 PRIOR MEMORY` line. These memories represent things the user already taught you on adjacent tasks — they constrain assumptions, surface preferences, and prevent re-litigating decisions. If the recall returns zero results, write `🧠 PRIOR MEMORY: none` and continue.

2. **LEARN — use Zettel as a deduplication and pattern-promotion engine (RECALL → DIFF → SAVE only novel → LINK recurrences → HUB patterns).**

   LEARN's memory purpose is NOT "dump every reflection into the bead store." It's to make the **next run** better by surfacing recurring blind spots. The recurrence itself is often more valuable than the content.

   **Step 1 — pre-reflection RECALL.** BEFORE answering the 4 reflection questions, run:
   ```bash
   zettel recall "{domain keywords from this run}" -l 10 -d connected
   ```
   Read the recalled beads. Ask: "what did I learn THIS time that isn't already in memory?" Not "what did I learn."

   **Step 2 — DIFF each of the 4 reflection answers against prior beads.** Classify each:

   | Classification | Action |
   |---|---|
   | **Novel** — no prior bead matches | Save a new bead (see Step 3 for type) |
   | **Restatement** — same lesson already exists as bead `br-XXX` | **Do NOT save a duplicate.** Instead `zettel link {new-pointer-bead} br-XXX reinforces`. Note `(reinforces br-XXX)` in the PRD. The recurrence IS the signal. |
   | **Reinforcement with a new angle** | Save the new angle only, `zettel link` to the original |
   | **Clean run — nothing to note** | Don't save. JSONL still records the run; a bead would be clutter |

   **Step 3 — SAVE only the novel, using precise types (not all `learning`):**
   ```bash
   # Q1 "should have done differently" → learning (process) OR signal (mistake-to-warn-about)
   zettel save "{q1}" -t learning -S "algorithm-{slug}-learn"
   # Q2 "smarter algorithm" → learning (algorithmic pattern) OR fact (reusable technique like a regex)
   zettel save "{q2}" -t learning -S "algorithm-{slug}-learn"
   # Q3 "capabilities unused" → preference (use X by default next time) OR learning (X exists, consider)
   zettel save "{q3}" -t preference -S "algorithm-{slug}-learn"
   # Q4 "smarter AI design" → learning (meta-improvement)
   zettel save "{q4}" -t learning -S "algorithm-{slug}-learn"
   ```

   **Step 4 — Promote recurring patterns to hubs.** If the SAME lesson has been recalled/linked **3+ times** across runs, create a structure note:
   ```bash
   zettel hub topic-hub "recurring-{pattern-name}"
   ```
   Then `zettel link` the 3+ individual beads into the hub's neighborhood. Hubs have higher centrality in the Zettelkasten graph, so future OBSERVE recalls hit them first. This is how knowledge **graduates** from isolated lessons to navigable canon.

   **Step 5 — Capture IDs in PRD.** Write all new bead IDs AND any `(reinforces br-XXX)` references into the PRD's `## Verification` section under `### Memory beads`. If `zettel save` fails (engine unavailable), note once in `## Decisions` and continue — JSONL is the durable record, beads are the surfaceable one.

   **What LEARN memory is NOT for:** duplicating what JSONL already captures (criteria counts, timestamps, sentiment are machine-mined), saving "nothing to note" reflections, saving all 4 answers as `learning` when they're actually a mix of types.

**Three optional integration points (use when natural):**

3. **THINK — use Zettel as a threat oracle (RECALL-first, SAVE-last).**

   THINK is adversarial reasoning against your own plan. Each assumption and premortem item is itself a searchable concept — queries that didn't exist yet at OBSERVE time. OBSERVE recalls on the task title; THINK recalls **per-risk**, narrowly.

   **Primary — per-risk RECALL:** For each riskiest assumption AND each premortem scenario, run a targeted query:
   ```bash
   zettel recall "{assumption or failure mode keywords}" -l 3 -d flat
   ```
   A hit means "this exact failure has bitten a prior run — it's confirmed, not hypothetical." When a recall hits:
   - Surface in THINK output with the bead ID: `⚠️ PRIOR SIGNAL: {content} (br-XXX)`
   - **Promote the risk into a new ISC** that references the bead so the audit trail is traceable. Example: `ISC-N: URL validation regex rejects shell metacharacters (per br-dus)`.
   - **Apply the known mitigation from the recalled bead directly** instead of re-deriving it from scratch. If the bead contains the exact fix (regex, config flag, sequence), use it verbatim.

   **Secondary — capability-selection RECALL:** Before confirming the OBSERVE CAPABILITY SELECTION, run:
   ```bash
   zettel recall "Skill simplify effectiveness" -l 3
   ```
   This surfaces prior LEARN beads that act as **priors** committing you to capabilities that have historically caught real issues on tasks like this one. This is how capability commitment becomes evidence-based.

   **Tertiary — SAVE only novel risks:** If a premortem risk has NO prior bead AND it's non-obvious, save it as `signal` with source tag `algorithm-{slug}-think`. If the recall already surfaced the same risk, **do NOT re-save** — it's already in memory, re-saving dilutes search scores.

   **What THINK memory is NOT for:** saving the whole assumption list every run, saving prerequisites (they belong in the PRD), saving mitigations (they belong in ISC).

4. **EXECUTE — SAVE non-obvious decisions as facts.** When you make a decision the user would not have predicted from the request (a path choice, a library swap, a refactor scope), `zettel save "{decision} (reason: {why})" -t fact -S "algorithm-{slug}-execute"`. These become the audit trail.

5. **VERIFY — SAVE surprising verification findings as signals.** When verification reveals something you didn't expect (a remote/local divergence, a hidden cache, a flaky dependency), `zettel save "{finding}" -t signal -S "algorithm-{slug}-verify"`. These prevent the same surprise next time.

**Memory failure mode handling.** If `zettel status` returns `available: false`, or any zettel call fails, log it once in the PRD under `## Decisions` ("zettel unavailable, memory integration skipped this run") and continue without memory. Never block Algorithm progress on memory unavailability — the engine is best-effort, the work is mandatory.

**What NOT to save.** Do not save: trivial outputs of single tool calls, raw search results, intermediate reasoning, content already captured in the PRD verbatim, or content that duplicates what `git log`/`git blame` already records. Memory is for things that would otherwise be **forgotten between runs** — preferences, surprises, costly lessons, durable facts about the user's environment.

### Card Lifecycle States — A Conversational Handshake

Memory cards have four lifecycle states. They are **NOT** task-tracker statuses borrowed from the issue-tracker substrate — they are a **session protocol** that lets a stateless LLM maintain continuity with the user across invocations.

| State | Semantic | Default? |
|---|---|---|
| `open` | Developable; part of the library; no specific blocker | **Yes — for almost all saves** |
| `in_progress` | The user's current focus. Resume hook on next session. | Only when explicitly starting a research session on this topic |
| `blocked` | Depends on stub cards that need development first | Only when content references missing anchors |
| `closed` | Thread terminus along this folgezettel chain; saturated reference | Only on explicit user instruction |

#### Mandatory: OBSERVE Resumption Check

After the standard `zettel recall "{8-word task}"` at OBSERVE entry, run a **SECOND** query specifically for in-progress cards:

```bash
zettel recall --status in_progress -l 10 -d connected
```

The recall returns the unlimited in_progress set. If ANY results come back, surface them under `🧠 PRIOR MEMORY` BEFORE the regular recall hits.

**Step 1 — classify each in_progress card by relevance to the new request.** For each result, ask: "would resuming this card *be* the same task as what the user just asked, or would it be a different task?" Emit a relevance marker:

| Marker | Meaning |
|---|---|
| ←→ matches | Resuming this card IS the new request. Same task title, same domain, same files. |
| ⊃ overlaps | The new request is a sub-task or extension of this card's work. Resuming would broaden scope. |
| ⊥ unrelated | The new request is on a different topic. Resuming would mean *abandoning* the in_progress work. |

**Step 2 — pick the right output format based on what the classifier found.**

**Format A — at least one ←→ matches hit (most common: user came back to finish something):**
```
🧠 RESUMPTION:
  scope:{scope-a} — N in progress
    • ←→ "{title}" (br-XXX, {time-ago}) ← matches current task
    • "{title}" (br-YYY, {time-ago})
Resume the matching card, or treat current request as fresh? (default: resume)
```

**Format B — only ⊥ unrelated hits (Tier 2 pivot prompt — user has open work but is starting something new):**
```
🧠 RESUMPTION — UNRELATED PIVOT DETECTED:
  You have N card(s) in_progress on a different topic than your new request:
    • ⊥ "{title}" (br-XXX, {time-ago}) — last worked: {scope}
    • ⊥ "{title}" (br-YYY, {time-ago}) — last worked: {scope}

  Your new request: "{8-word task description}"

  Three options:
    1. RESUME the existing in_progress work — I'll abandon the new request and pick up {br-XXX}.
    2. KEEP IN PROGRESS and treat the new request as fresh — the existing card stays as-is and surfaces again next session. (default for explicit pivots)
    3. MARK COMPLETE and treat the new request as fresh — the existing card moves to closed (you're saying it's done), and the new request runs without resumption baggage.

  Which? (1 / 2 / 3)
```

**Format C — ⊃ overlaps hits (the new request extends existing work):**
```
🧠 RESUMPTION — OVERLAP DETECTED:
  Your new request looks like an extension of in_progress work:
    • ⊃ "{title}" (br-XXX, {time-ago})

  Should I treat this as continuing that work (recommended — keeps the resume hook coherent) or as a separate task?
```

**Format D — no in_progress hits at all:**
```
🧠 RESUMPTION: none
```
…and continue without pause.

**Step 3 — PAUSE for user input on Formats A, B, and C.** This is one of the few places the Algorithm explicitly waits — resumption is too important to autopilot. Format D continues automatically.

**Step 4 — apply the user's choice IMMEDIATELY before proceeding to reverse engineering.**

| User picked | Action |
|---|---|
| Format A "resume" | Read the matching card's PRD pointer, set the current run's slug to that card's slug, set effort to whatever resume-state implies. |
| Format A "fresh" | Treat as new task. The matching card stays in_progress and Format B logic will kick in next session. |
| Format B option 1 (RESUME) | Same as Format A "resume" — abandon the new request, pick up br-XXX. |
| Format B option 2 (KEEP) | No state change. Continue with the new request. The existing card surfaces again next session. **This is the dominant pivot pattern — most "let's switch to X" requests land here.** |
| Format B option 3 (MARK COMPLETE) | Run `zettel promote {br-XXX} --to closed --reason "{user's reason or 'pivot 2026-MM-DD'}"`. Then continue with the new request. Use sparingly — closing a card you didn't actually finish is destructive of the resume signal. |
| Format C "extend" | Set current run's slug to the existing card's slug. Update the card's title later in LEARN to reflect the broader scope. |
| Format C "separate" | Treat as new task. Existing card stays in_progress. |

**Why this exists.** Without the pivot prompt, the Algorithm silently inherits whatever the previous session was working on, OR silently abandons it without telling the user. Both are wrong. Format B forces an explicit decision exactly at the moment when context is freshest — the user just typed their new request and is in the headspace to say whether the old work still matters. Trying to make this decision later (mid-execute, or in LEARN) is too late.

#### Save-side state inference

When saving a card (via `zettel save` or the Algorithm's EXECUTE/LEARN hooks), infer the correct status from the user's verbs. First match wins:

| Verb pattern | Status |
|---|---|
| "I'm working on", "I'm starting", "let's research", "let me explore" | `in_progress` |
| "I'm done with", "that's settled", "no more to add", "finished with" | `closed` |
| "I need X first", "blocked on", "can't do this without", "depends on X" | `blocked` (see stub flow below) |
| anything else | `open` (default) |

**Always announce the inference.** E.g. "Saved as `in_progress` because you said 'working on'." or "Saved as `open` (default) — let me know if this is your current focus."

When verb patterns conflict, prefer the more cautious state: `open > in_progress > blocked > closed`. Closed is the hardest to reverse.

#### Stub creation pattern (when status would be `blocked`)

When the user describes a card whose body references concepts that DON'T EXIST yet (verify via `zettel recall "{concept}" -l 1` returning empty), do NOT save the card directly. Instead:

1. Identify the missing anchors (typically 1-3).
2. Propose: "I'll create stubs for {concept-a} and {concept-b}, then save the main card as `blocked`. OK?"
3. On confirmation, create each stub first: `zettel save "{Concept} (stub)" --kind stub --status open`
4. Then save the main card with explicit edges: `zettel save "{full content}" --status blocked --blocked-by $STUB1 --blocked-by $STUB2`
5. Show all returned IDs so the user can develop the stubs later.

This pattern keeps the graph navigable: every blocked card has explicit `blocks` edges to developable targets, and the auto-transition hook can flip the blocked card to `open` once all its stubs are promoted.

#### Engine-side auto-transitions and notifications

The engine auto-flips `blocked → open` when all of a card's `blockedBy` targets lose their `kind:stub` label (i.e. get developed). Auto-transitions emit an `unblocked` event to `~/.cosmic-agent/notifications.jsonl`, which SessionStart hooks read and surface in the dynamic context block. Similarly, `in_progress` cards with no edits in 7+ days produce `stale_in_progress` notifications so the resume channel doesn't rot.

**Never manually promote `blocked → open` without `--force`.** That transition belongs to the engine; bypassing it defeats the handshake. The only legitimate manual use of `promote --force` on a blocked card is explicit user override ("yes, unblock this anyway").

**Anti-criteria** (ISC-A prefix): what must NOT happen.

### ISC Decomposition Methodology

**The core principle: each ISC criterion = one atomic verifiable thing.** If a criterion can fail in two independent ways, it's two criteria. Granularity is not optional — it's what makes the system work. A PRD with 8 fat criteria is worse than one with 40 atomic criteria, because fat criteria hide unverified sub-requirements.

**The Splitting Test — apply to EVERY criterion before finalizing:**

1. **"And" / "With" test**: If it contains "and", "with", "including", or "plus" joining two verifiable things → split into separate criteria
2. **Independent failure test**: Can part A pass while part B fails? → they're separate criteria
3. **Scope word test**: "All", "every", "complete", "full" → enumerate what "all" means. "All tests pass" for 4 test files = 4 criteria, one per file
4. **Domain boundary test**: Does it cross UI/API/data/logic boundaries? → one criterion per boundary

**Decomposition by domain:**

| Domain | Decompose per... | Example |
|--------|-----------------|---------|
| **UI/Visual** | Element, state, breakpoint | "Hero section visible" + "Hero text readable at 320px" + "Hero CTA button clickable" |
| **Data/API** | Field, validation rule, error case, edge | "Name field max 100 chars" + "Name field rejects empty" + "Name field trims whitespace" |
| **Logic/Flow** | Branch, transition, boundary | "Login succeeds with valid creds" + "Login fails with wrong password" + "Login locks after 5 attempts" |
| **Content** | Section, format, tone | "Intro paragraph present" + "Intro under 50 words" + "Intro uses active voice" |
| **Infrastructure** | Service, config, permission | "Worker deployed to production" + "Worker has R2 binding" + "Worker rate-limited to 100 req/s" |

**Granularity example — same task at two decomposition depths:**

Coarse (8 ISC — WRONG for Extended+):
```
- [ ] ISC-1: Blog publishing workflow handles draft to published transition
- [ ] ISC-2: Markdown content renders correctly with all formatting
- [ ] ISC-3: SEO metadata generated and validated for each post
```

Atomic (showing 3 of those same areas decomposed to ~12 criteria each):
```
Draft-to-Published:
- [ ] ISC-1: Draft status stored in frontmatter YAML field
- [ ] ISC-2: Published status stored in frontmatter YAML field
- [ ] ISC-3: Status transition requires explicit user confirmation
- [ ] ISC-4: Published timestamp set on first publish only
- [ ] ISC-5: Slug auto-generated from title on draft creation
- [ ] ISC-6: Slug immutable after first publish

Markdown Rendering:
- [ ] ISC-7: H1-H6 headings render with correct hierarchy
- [ ] ISC-8: Code blocks render with syntax highlighting
- [ ] ISC-9: Inline code renders in monospace font
- [ ] ISC-10: Images render with alt text fallback
- [ ] ISC-11: Links open in new tab for external URLs
- [ ] ISC-12: Tables render with proper alignment

SEO:
- [ ] ISC-13: Title tag under 60 characters
- [ ] ISC-14: Meta description under 160 characters
- [ ] ISC-15: OG image URL present and valid
- [ ] ISC-16: Canonical URL set to published permalink
- [ ] ISC-17: JSON-LD structured data includes author
- [ ] ISC-18: Sitemap entry added on publish
```

The coarse version has 3 criteria that each hide 6+ verifiable sub-requirements. The atomic version makes each independently testable. **Always write atomic.**
